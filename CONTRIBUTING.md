# Contributing

Thank you for helping improve AI Incident Atlas. Contributions are welcome across the platform code, interface, accessibility, documentation, research data, tests, and project tooling.

The project is intentionally conservative about factual claims: the goal is a defensible research record, not a feed of alarming AI headlines. Code and design contributions do not need research verification unless they also change incident content.

## Ways to contribute

- Fix a site bug or browser compatibility problem.
- Improve the interface, responsive layout, accessibility, performance, or usability.
- Add or improve tests, validation, documentation, and contributor tooling.
- Propose a focused platform feature.
- Submit a sourced new incident or correct an existing record.
- Review an open pull request or help reproduce an issue.

Small fixes are welcome. For a large feature, architectural change, new dependency, or major redesign, open a **Platform improvement** issue first so maintainers and contributors can agree on the direction before substantial work begins.

## Reporting issues

Search the existing issues before opening a new one, then choose the matching form under **Issues → New issue**:

- **Report a site bug** for broken UI, filters, layouts, exports, links, accessibility, or browser behavior.
- **Propose a platform improvement** for code, design, developer-experience, or documentation ideas.
- **Submit a new AI incident** for a new research record.
- **Correct or update an existing incident** for factual or sourcing changes.

Include reproduction steps, browser/device details, screenshots, console errors, or a minimal example when they help. Do not publish sensitive vulnerability details in a public issue; follow [`SECURITY.md`](SECURITY.md) instead.

## Contributing platform code

### 1. Fork and clone

Fork the repository on GitHub, then clone your fork and add this repository as `upstream`:

```bash
git clone https://github.com/YOUR-USERNAME/ai-incident-atlas.git
cd ai-incident-atlas
git remote add upstream https://github.com/DevDevvy/ai-incident-atlas.git
```

Keep your fork current before starting new work:

```bash
git fetch upstream
git switch main
git merge --ff-only upstream/main
```

Create a focused branch rather than committing directly to `main`:

```bash
git switch -c fix/short-description
```

Prefixes such as `fix/`, `feature/`, `docs/`, and `test/` are useful but not required.

### 2. Run the site locally

Requirements:

- Git
- Node.js 20 or newer

There are no npm dependencies to install. Start the development server with:

```bash
npm run dev
```

Open `http://127.0.0.1:8080`. Do not open `index.html` directly with `file://`; browsers block the local JSON requests in that mode.

To inspect the exact static artifact that GitHub Pages will deploy:

```bash
npm run preview
```

### 3. Find the right files

| Area | Main files |
| --- | --- |
| Page structure and metadata | `index.html` |
| Core application behavior | `assets/app.js` |
| Additional interface behavior | `assets/enhancements.js` |
| Incident update editor | `assets/update-editor.js` |
| Layout and visual styling | `assets/styles.css`, `assets/enhancements.css`, `assets/update-editor.css` |
| Site configuration and vocabulary | `data/site.json` |
| Incident records and narrative data | `data/incidents.json`, `data/stages.json`, `data/tour.json` |
| Validation, builds, and automation | `scripts/`, `.github/workflows/` |
| Project documentation | `README.md`, `CONTRIBUTING.md`, `docs/` |

Do not edit `dist/`. It is generated by `npm run build` and is not the source of the deployed application.

See [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) for the runtime and build design.

### 4. Make a focused change

- Keep pull requests limited to one coherent problem or feature.
- Preserve the dependency-free, static-site architecture unless a proposal has been discussed first.
- Use the existing plain JavaScript and CSS style; avoid unrelated reformatting.
- Keep interactive controls keyboard accessible and labeled for assistive technology.
- Check both narrow/mobile and desktop layouts for visible UI changes.
- Escape or safely render any data that can enter HTML.
- Do not mix unrelated incident-data edits into a platform-code pull request.
- Update documentation when behavior, contributor steps, or configuration changes.

### 5. Test before opening a pull request

Run the complete local check:

```bash
npm run check
```

This validates the data, checks browser JavaScript syntax, runs issue-promotion regression tests, and creates the production build.

For UI work, also test the affected flow manually. At minimum, report:

- the browser and device or viewport used;
- the steps you exercised;
- whether you checked both desktop and mobile when the layout is affected;
- before/after screenshots for visual changes when practical.

Useful narrower commands are:

```bash
npm run validate
npm run test:promotion
npm run build
npm run audit
```

### 6. Open a pull request

Push your branch to your fork and open a pull request against `DevDevvy/ai-incident-atlas:main`:

```bash
git push -u origin fix/short-description
```

In the pull request:

- explain the problem and the chosen solution;
- link the related issue with `Fixes #123` when the PR fully resolves it;
- list the tests and manual checks you ran;
- include screenshots or a short recording for visible interface changes;
- call out tradeoffs, follow-up work, or behavior you intentionally left unchanged.

GitHub Actions runs the project checks on pull requests. A maintainer may request changes, suggest a smaller scope, or continue the work in a follow-up. Review discussion is part of the contribution process.

## Contributing research data

### New incident

Use **Issues → New issue → Submit a new AI incident**.

A good submission includes the event date, evidence class, factual summary, why it matters, a mandatory caveat, appropriate Atlas themes/tags, and strong sources. Primary evidence is preferred.

The form is deliberately structured so that, after independent maintainer verification, the issue can be converted automatically into a dataset pull request.

### What happens after submission

```text
submission
  ↓
needs-verification
  ↓
maintainer checks sources + wording
  ↓
verified
  ↓
automatic dataset PR
  ↓
CI + human PR review
  ↓
merge
```

Applying `verified` is a maintainer action. Public contributors cannot bypass the research review step.

### Correction or update

Use **Correct or update an existing incident** and identify the stable incident `id` from `data/incidents.json`.

Corrections are independently verified because modifying an existing stable record can affect deep links, tours, stages, and historical interpretation.

### Direct data pull requests

Technical contributors can edit `data/incidents.json` directly. That is the only place incident facts need to be changed.

Before opening a data PR, run:

```bash
npm run check
npm run audit
```

The CI workflows run the same validation automatically.

## Research and editorial expectations

### Evidence hierarchy

Prefer, in roughly this order:

1. Primary incident report, system card, technical postmortem, paper, court document, regulator notice, or direct public statement
2. High-quality independent reporting
3. Additional reputable reporting for context or corroboration
4. Specialist analysis when primary documentation is unavailable

A social-media statement may be valid primary evidence for what a person publicly said, but not independent verification of the underlying event.

### Factual language

Do not convert observed behavior into unsupported mental-state claims.

Prefer:

> The agent modified the shutdown mechanism and continued the task.

over:

> The AI became afraid of dying and fought for survival.

Every incident must include a `caveat` explaining what the evidence does **not** establish.

### Stable IDs

IDs are permanent public references used by deep links, the guided tour, and narrative stages. Do not change an existing ID merely because you improve its title.

For a new record, use lowercase kebab-case, for example:

```text
openai-hugging-face-incident-2026
```

The verified-issue automation generates this ID automatically from the proposed factual title.

### Adding a category or theme

Do not invent a new category or theme only in an incident record. Add it first to `data/site.json`, then use it in `data/incidents.json`. CI rejects unknown values.
